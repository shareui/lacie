## 1. Обзор и архитектура

Lacie рассматривает пакеты как неизменяемые декларативные артефакты. Ключевые архитектурные решения:
- **Воркспейсы:** один файл `lacie.toml` может описывать сразу несколько отдельных пакетов, разделяющих общие метаданные, версию или бинарники.
- **Нулевое доверие:** бинарные файлы обязаны содержать контрольные суммы SHA256. Любые скрипты жизненного цикла фиксируются по хэшу в `scripts.toml` при первом подтверждении пользователем.
- **Модульные источники:** реестры пакетов (GitHub, GitLab, произвольные HTTP/S3-сервисы) реализованы как изолированные внешние плагины, взаимодействующие с ядром Lacie по протоколу JSON-RPC через стандартные потоки ввода-вывода.

## 2. Спецификация манифеста (`lacie.toml`)

Файл `lacie.toml` содержит описание пакетов, бинарников для различных платформ, зависимостей и хуков.

### Структура воркспейса

Манифест состоит из общей секции `[workspace]` и одной или нескольких секций `[packages."<id>"]`.

```toml
[workspace]
author = "shareui"
version = "1.0.0"
version_number = 1
source_code = "https://github.com/shareui/lacie"
links = ["https://example.com"]

[packages."com.example.app"]
name = "app"

[packages."com.example.app".binaries."linux-gnu-x86_64"]
file = "app-linux-x86_64"
sha256 = "3f2a9c0e41b7d2a85c6f0e19b4d7a3c28e5f1096ab7d4c3e2f81b0a9d6c57e43"
```

#### Правила наследования
- Ключи из `[workspace]` служат значениями по умолчанию для всех пакетов.
- Секция пакета переопределяет значения из `[workspace]`.
- Переопределение заменяет значение целиком; массивы не объединяются.
- Поля `name` и `binaries` запрещено указывать в `[workspace]`; они задаются строго в конкретном пакете.

---

### Описание пакета (`[packages."<id>"]`)

Идентификатор пакета (ID) задается в формате обратного домена (`com.domain.tool`). Он обязан содержать как минимум одну точку, состоять из строчных латинских букв, цифр, дефисов или подчеркиваний, и иметь длину от 3 до 128 символов.

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `name` | string | **Да** | Отображаемое имя пакета и имя исполняемой команды по умолчанию. |
| `version` | string | **Да** | Строка семантической версии (например, `1.2.0`). |
| `version_number` | integer | Нет | Монотонно возрастающий целочисленный счетчик сборки/релиза. |
| `author` | string | Нет | Автор пакета или организация. |
| `source_code` | string | Нет | Ссылка на репозиторий исходного кода. |
| `links` | array of strings | Нет | Ссылки на документацию или сайт проекта. |
| `required` / `requires` | array of strings | Нет | Список сопутствующих обязательных пакетов, устанавливаемых вместе с данным. |
| `apps` | array of tables | Нет | Внешние исполняемые утилиты-зависимости. |
| `libs` | array of tables | Нет | Библиотеки и ресурсные зависимости. |
| `check_deps` | string | Нет | Относительный путь к скрипту проверки зависимостей. |
| `prebuild` | string | Нет | Относительный путь к скрипту перед установкой. |
| `postbuild` | string | Нет | Относительный путь к скрипту после установки. |
| `preremove` | string | Нет | Относительный путь к скрипту перед удалением. |
| `postremove` | string | Нет | Относительный путь к скрипту после удаления. |

---

### Целевые платформы (таргеты)

Исполняемые файлы описываются по платформенным триплам `{os}-{abi}-{arch}` (или `{os}-{arch}`, если в ОС нет выбора ABI):

| Таргет | Платформа |
|---|---|
| `linux-gnu-x86_64`, `linux-gnu-aarch64` | Linux с glibc |
| `linux-musl-x86_64`, `linux-musl-aarch64` | Linux с musl libc |
| `windows-msvc-x86_64`, `windows-msvc-aarch64` | Windows 11 (MSVC runtime) |
| `windows-mingw-x86_64` | Windows 11 (MinGW runtime) |
| `macos-aarch64`, `macos-x86_64` | macOS (Apple Silicon / Intel) |
| `freebsd-x86_64`, `openbsd-x86_64` | FreeBSD / OpenBSD |

---

### Определение бинарников (`[packages."<id>".binaries."<таргет>"]`)

Каждая таблица таргета **обязана определять ровно один** из ключей: `file`, `links` или `source`. Указание нескольких или отсутствие всех приводит к ошибке валидации `E028`.

```toml
# 1. Имя ассета релиза или относительный путь к файлу
[packages."com.example.tool".binaries."linux-gnu-x86_64"]
file = "tool-linux-x86_64.tar.gz"
sha256 = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"

# 2. Прямые ссылки на скачивание с резервными зеркалами
[packages."com.example.tool".binaries."windows-msvc-x86_64"]
links = [
  "https://cdn.example.com/tool-windows.zip",
  "https://backup.example.com/tool-windows.zip"
]
sha256 = "b81d02c7aa90e4f35d6218cb07a9e3f4152d8c60b7e9a14f03d5c28e6b79a1f0"

# 3. Делегирование сборки другому репозиторию
[packages."com.example.tool".binaries."macos-aarch64"]
source = "github:shareui/tool-macos#com.example.tool"
```

#### Справочник ключей бинарника
- `file`: имя файла ассета в текущем релизе или относительный путь для локальных манифестов.
- `links`: массив прямых ссылок на файл; опрашиваются по порядку как зеркала.
- `source`: ссылка на внешний пакет в стандартном формате (`source:owner/repo#pkg`).
- `sha256`: шестнадцатеричный SHA256-хэш архива или бинарника.
- `size`: ожидаемый размер в байтах (необязательно, при отсутствии опрашивается API источника).
- `static`: логический флаг. Установите `true`, если бинарник статически слинкован и не зависит от libc.

---

### Правила фоллбеков платформ

Lacie применяет детерминированные правила выбора альтернативных сборок:

1. **Linux (glibc -> musl):**
   - На системах с glibc (`linux-gnu-*`), если сборка под GNU отсутствует, Lacie предлагает сборку `linux-musl-*` **только при условии**, что указан флаг `static = true` либо в системе обнаружен `ld-musl-{arch}.so.1` в `/lib`.
   - На системах с musl (например, Alpine) glibc-бинарники запускаться не могут, поэтому обратный фоллбек отсутствует.

2. **Windows 11 (MSVC <-> MinGW):**
   - Приоритет определяется параметром `windows_priority` (по умолчанию `msvc`).
   - Если приоритетная сборка отсутствует, Lacie выдает предупреждение `W003` и запрашивает разрешение на установку альтернативного ABI.

---

### Обязательные сопутствующие пакеты (`required`)

Пакет может объявлять другие пакеты, которые должны быть гарантированно установлены вместе с ним:

```toml
[packages."com.example.editor"]
name = "editor"
version = "2.0.0"
required = ["github:shareui/treesitter-parser", "com.example.linter"]
```

При выполнении команды `lacie add editor` менеджер транзитивно находит и добавляет в очередь установки все зависимости из поля `required` (или `requires`).

---

### Зависимости (`apps` и `libs`)

- `apps`: внешние утилиты командной строки, необходимые для работы пакета:
  ```toml
  apps = [
    { id = "org.git.git", from = "github:git/git", min_number = 10 }
  ]
  ```
- `libs`: разделяемые библиотеки или ресурсы, размещаемые в подкаталоге пакета:
  ```toml
  libs = [
    { id = "org.openssl.libssl", from = "github:openssl/openssl", dest = "lib" }
  ]
  ```

---

### Валидация манифеста

Мейнтейнеры могут локально проверить корректность `lacie.toml` перед публикацией релиза:

```bash
lacie validate ./lacie.toml
```

Команда проверяет соответствие схемы, корректность имен таргетов и сверяет SHA256 с локальными файлами, если они находятся в каталоге.

## 3. Скрипты жизненного цикла (хуки)

Lacie позволяет запускать Ruby-скрипты на ключевых этапах установки и удаления.

### Доступные хуки

| Хук | Момент вызова | Назначение |
|---|---|---|
| `check_deps` | До начала установки | Проверяет системные требования и окружение. |
| `prebuild` | После скачивания, до активации | Компиляция, подготовка и распаковка дополнительных ресурсов. |
| `postbuild` | После создания активного бинарника | Генерация начального конфига, автодополнений, кэшей. |
| `preremove` | До удаления/деактивации | Остановка фоновых служб, резервное копирование данных. |
| `postremove` | После удаления файлов бинарника | Очистка кэшей и временных каталогов. |

### Контекст выполнения и ограничения

Скрипты исполняются интерпретатором Ruby в изолированном временном каталоге внутри `var/`.
- Рабочим каталогом являются распакованные файлы пакета.
- Скрипт обязан завершаться с кодом `0` в случае успеха. Ненулевой код завершения прерывает операцию.

### Безопасность и проверка целостности (`scripts.toml`)

Для предотвращения атак на цепочку поставок:
1. При установке пакета с хуками `preremove` или `postremove` Lacie вычисляет SHA256-хэш скриптов и записывает его в доверенную базу `scripts.toml`.
2. При удалении пакета (`lacie remove`) хэш скрипта вычисляется заново.
3. Если хэш изменился по сравнению с `scripts.toml`, выполнение блокируется с ошибкой `E035`.
4. Пользователь может отключить выполнение скриптов удалением флагом `--no-scripts`.

## 4. Архитектура плагинов источников

Плагин источника связывает Lacie с удаленными реестрами, индексами пакетов или хранилищами.

### Структура каталога плагина

Плагины размещаются в `plugins/{имя_источника}/`:
```
plugins/
└── custom_source/
    ├── source.toml       # Манифест плагина
    └── custom_source.rb  # Исполняемая точка входа RPC
```

---

### Манифест плагина (`source.toml`)

```toml
name = "custom"
id = "org.example.custom"
author = "Your Name"
version = "0.1.0"
version_number = 1
api = 1
entry = "custom.rb"
capabilities = ["search"]
env = ["CUSTOM_API_KEY"]

[[files]]
path = "custom.rb"
executable = true
```

#### Справочник полей манифеста
- `name`: имя источника для вызова из CLI (`custom:owner/repo`). От 2 до 32 символов, латиница, цифры, дефис.
- `id`: уникальный доменный идентификатор плагина.
- `api`: версия протокола интеграции. На данный момент должна быть равна `1`.
- `entry`: относительный путь к исполняемому файлу точки входа.
- `capabilities`: поддерживаемые опциональные функции (например, `["search"]`).
- `env`: список переменных окружения, пробрасываемых в подпроцесс плагина.
- `files`: состав файлов плагина для дистрибуции и проверки целостности.

---

### Протокол JSON-RPC через stdio

Lacie запускает процесс плагина и обменивается сообщениями по протоколу JSON-RPC 2.0 через стандартные потоки `stdin` и `stdout`. Каждое сообщение передается строго одной строкой, оканчивающейся на `\n`.

#### Структура запроса
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "releases",
  "params": {
    "storage": "owner/repo"
  }
}
```

#### Структура успешного ответа
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [ ... ]
}
```

#### Структура ошибки
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32000,
    "message": "Repository not found"
  }
}
```

---

### Справочник методов RPC

#### 1. `releases`
Возвращает список доступных релизов хранилища.
- **Параметры:** `{"storage": "owner/repo"}`
- **Результат:** массив объектов релизов:
  ```json
  [
    {
      "tag": "v1.2.0",
      "pre_release": false,
      "published_at": "2026-03-01T12:00:00Z",
      "has_manifest": true
    }
  ]
  ```

#### 2. `manifest`
Возвращает сырой текст `lacie.toml` для указанного релиза.
- **Параметры:** `{"storage": "owner/repo", "release": "v1.2.0"}`
- **Результат:** строка с содержимым файла манифеста.

#### 3. `search` (Опционально, требует возможность `"search"`)
Ищет пакеты по строковому запросу.
- **Параметры:** `{"query": "поисковая-строка"}`
- **Результат:** массив результатов поиска:
  ```json
  [
    {
      "storage": "owner/repo",
      "stars": 42
    }
  ]
  ```

#### 4. `fetch`
Скачивает ассет релиза в указанный файл на диске.
- **Параметры:** `{"storage": "owner/repo", "release": "v1.2.0", "file": "asset.tar.gz", "dest": "/абсолютный/путь/назначения"}`
- **Результат:** `null` при успешной загрузке.

### Пример реализации собственного плагина

Минимальный пример рабочего плагина на Ruby (`custom.rb`):

```ruby
#!/usr/bin/env ruby
require 'json'

STDOUT.sync = true

while (line = STDIN.gets)
  req = JSON.parse(line.strip)
  id = req['id']
  method = req['method']
  params = req['params'] || {}

  case method
  when 'releases'
    storage = params['storage']
    result = [
      {
        'tag' => '1.0.0',
        'pre_release' => false,
        'has_manifest' => true
      }
    ]
    puts JSON.generate({ 'jsonrpc' => '2.0', 'id' => id, 'result' => result })

  when 'manifest'
    toml = <<~TOML
      [workspace]
      version = "1.0.0"

      [packages."org.custom.tool"]
      name = "tool"

      [packages."org.custom.tool".binaries."linux-gnu-x86_64"]
      links = ["https://custom.example.com/tool-linux"]
      sha256 = "01ba4719c80b6fe911b091a7c05124b64eeece964e09c058ef8f9805daca546b"
    TOML
    puts JSON.generate({ 'jsonrpc' => '2.0', 'id' => id, 'result' => toml })

  when 'search'
    query = params['query']
    result = [
      { 'storage' => "custom/#{query}", 'stars' => 10 }
    ]
    puts JSON.generate({ 'jsonrpc' => '2.0', 'id' => id, 'result' => result })

  else
    err = { 'code' => -32601, 'message' => "Method not found: #{method}" }
    puts JSON.generate({ 'jsonrpc' => '2.0', 'id' => id, 'error' => err })
  end
end
```
